## Step 3 rules: flood extent (fixed before any flood area was computed)

These rules were written and committed before any flood area was computed
(see the git history of `scripts/step3_rules.md`). They are copied into
METHODS.md unchanged. The result is not to be adjusted toward any published
figure.

**Rules set by the project owner**

1. Water threshold: the 2014-09-10 Otsu value from step 2 (0.127), applied
   to both dates.
2. Analysis area: valley floor (DEM <= 1,800 m) connected to Srinagar only.
3. QA_RADSAT is downloaded for all four scenes with the usual checks, and
   pixels saturated in green or SWIR1 are masked.
4. Pixels with SWIR1 reflectance <= 0 and green > 0 count as water. Pixels
   with both <= 0 stay masked.
5. Cirrus stays unmasked.
6. Flooded = water on 2014-09-10 and not water on 2014-08-25, among pixels
   valid on both dates.
7. The result is not to be adjusted toward any published figure.

**How the rules are implemented (fixed at the same time)**

- R1. The threshold is the value recorded in `data/water_report.json` for
  2014-09-10 (bin edge 0.127). Water = MNDWI > threshold (strictly greater),
  as in step 2.
- R2. Analysis area = DEM <= 1,800 m AND inside the 8-connected patch of such
  pixels that contains 34.08 N, 74.80 E (the patch used in step 2).
- R3. A pixel is saturated if QA_RADSAT bit 2 (band 3, green) or bit 5
  (band 6, SWIR1) is set, per the STAC `classification:bitfields`. QA_RADSAT
  is taken from the same row (036 or 037) that the mosaic used for that pixel
  (`*_source.tif`). Terrain occlusion (bit 11) is reported, not masked.
- R4. Pixels with green <= 0 and SWIR1 > 0 are not covered by rule 4; they
  stay masked, as in step 2 (MNDWI is not meaningful there).
- R5. Valid on a date = in the analysis area AND QA_PIXEL bits 0 (fill),
  1 (dilated cloud), 3 (cloud), 4 (cloud shadow), 5 (snow) all 0 AND not
  saturated (R3) AND not (green <= 0 and SWIR1 <= 0) AND not (green <= 0 and
  SWIR1 > 0). Water on a date = valid AND (MNDWI > threshold OR (SWIR1 <= 0
  and green > 0)).
- R6. Among pixels valid on both dates: flooded = water Sep and not water
  Aug; persistent water = water on both; water lost = water Aug and not
  water Sep. Not assessed = analysis area pixels not valid on at least one
  date.
- R7. Sensitivity variants change only the thresholds; masks are identical.
  (a) each date's own step 2 Otsu value as recorded (2014-08-25: -0.058;
  2014-09-10: 0.127), not recomputed after the new saturation mask;
  (b) 0 on both dates; (c) 0.077 and 0.177 on both dates.
- R8. Area = pixel count x 0.0009 km2 (30 m x 30 m UTM map units).
- R9. Srinagar box: lon 74.65 to 74.95, lat 33.95 to 34.20, the same pixel
  window as the step 1 previews.

**Unflagged clouds on 2014-09-10 (estimate only, masks not changed)**

Computed over analysis-area pixels valid on 2014-09-10. Thresholds are fixed
here, before looking at the result:

- U1. QA_PIXEL's own lower-confidence flag: cloud confidence (bits 8-9) =
  medium (2) while the cloud bit is 0.
- U2. Bright-and-white spectral test with the bands already downloaded:
  green, red, NIR and SWIR1 reflectance all > 0.20, AND
  (max - min) / mean of green, red, NIR < 0.7.
- U3. Shadow zone: pixels reached by moving each U2 pixel away from the sun
  (sun azimuth and elevation from the 2014-09-10 row 036 MTL) for cloud
  heights 500 m to 5,000 m in 250 m steps. Reported as the whole zone (upper
  bound) and the dark part of it (NIR < 0.15 and SWIR1 < 0.10).
- U4. Control: U2 is also applied to 2014-08-25 analysis-area pixels that
  QA_PIXEL flags clear (bit 6); the rate found there indicates how often the
  test fires on clear ground.
- U5. Reported: area of U1, U2, U3 (zone and dark part), and the flooded area
  falling inside each.

**OpenStreetMap water bodies and wetlands**

- O1. Overpass API query for the clip box: ways and relations tagged
  natural=water, natural=wetland, landuse=reservoir or waterway=riverbank.
  The raw response and the download time (UTC) are saved.
- O2. Closed ways and multipolygon relations are turned into polygons; a
  pixel is inside if its centre is inside any polygon. The OSM data are
  current, not from 2014.
- O3. Flooded area is split into inside and outside these polygons. If the
  download fails, the work stops.

**Independent check**

- I1. For each date, the water mask is cross-tabulated against QA_PIXEL bit 7
  (water) on valid analysis-area pixels: agreement, both disagreement
  directions, and Cohen's kappa. Bit 7 is produced by USGS from the same
  scene, so it is a check against a different algorithm, not against
  different data.

## Step 4 rules: buildings and roads (fixed before any count was computed)

These rules were written and committed before any building or road count was
computed (see the git history of `scripts/step4_rules.md`). They are copied
into METHODS.md unchanged.

**Rules set by the project owner**

1. Source: OpenStreetMap buildings (any building tag) and roads (highway
   tag) for the analysis area, fetched now. Record the download time, save
   the raw responses with checksums, and split the request into tiles if
   needed.
2. A building counts as flooded if its centroid falls in a flooded pixel of
   the step 3 flood mask. Also report the count using any overlap with a
   flooded pixel, as a sensitivity.
3. Road length is the length of road inside flooded pixels, in kilometres.
   Report motor roads (motorway down to residential, plus service,
   unclassified and living_street) as the main figure, and all other highway
   types separately.
4. Buildings and roads in pixels that were not assessed are reported as not
   assessed, not as dry.
5. The map is today's OpenStreetMap, not 2014's. This limitation is stated
   and not corrected for.

**How the rules are implemented (fixed at the same time)**

- B1. Download: Overpass API (same endpoint and client name as step 3),
  over the clip box (lon 74.2-75.4, lat 33.5-34.6) in tiles of 0.25 x 0.25
  degrees. A tile that fails is split into four, down to 0.0625 degrees; if
  a piece still fails after 3 attempts, the work stops. Each raw response is
  saved with its sha256 and download time. Elements appearing in more than
  one tile are kept once (by OSM type and id).
- B2. Buildings = nodes, ways and relations with a `building` key of any
  value (counts by value are reported, including `building=no` if present).
  Ways must be closed to form a polygon; relations are built from their
  outer/inner members as in step 3. Nodes are points.
- B3. Geometry is projected to the mosaic CRS (EPSG:32643). Centroid =
  polygon centroid (point itself for nodes). The centroid's pixel decides:
  flooded (flood class 1), assessed not flooded (0, 2, 3), not assessed
  (analysis-area pixel with class 255), or outside the analysis area.
  Totals are buildings whose centroid is in the analysis area.
- B4. Overlap sensitivity: the pixels a building touches (all-touched
  rasterisation on the 30 m grid; the centroid pixel for nodes). Flooded if
  any touched pixel is flooded; otherwise not assessed if any touched pixel
  is not assessed; otherwise dry. Total = buildings touching the analysis
  area.
- R1. Roads = ways with a `highway` key of any value. Ways tagged area=yes
  are areas, not lines: they are excluded from lengths and counted
  separately.
- R2. Motor roads (main figure): highway = motorway, motorway_link, trunk,
  trunk_link, primary, primary_link, secondary, secondary_link, tertiary,
  tertiary_link, residential, unclassified, service, living_street. Every
  other highway value is reported separately, by value.
- R3. Lengths: lines are clipped to the exact pixel outlines of the flooded,
  not-assessed and analysis-area pixels, in EPSG:32643 map units, reported
  in km. No correction for projection scale (under 0.05 % here) or slope.
- S1. Srinagar box: the step 3 pixel window (lon 74.65-74.95, lat
  33.95-34.20); buildings by centroid pixel, roads clipped to the window
  outline.
- W1. Inside / outside water and wetland: the step 3 OSM pixel mask
  (`data/osm/water_wetland_mask.tif`); buildings by centroid pixel, roads
  clipped to the mask's pixel outlines.

**Areas within Srinagar**

- A1. Query the Srinagar box for boundary=administrative relations (all
  admin_level values) and for place=suburb, neighbourhood or quarter (nodes,
  ways, relations).
- A2. Candidate polygon sets: each admin_level separately, and the set of
  place polygons. Coverage of a set = share of the analysis-area buildings
  (by centroid) in the Srinagar box that fall inside one of its polygons.
  Only sets with at least 5 polygons in the box count as areas within the
  city.
- A3. If a candidate set has coverage >= 90 %, the finest one (highest
  admin_level; place polygons preferred over admin if both qualify) is used.
  Otherwise a 1 km grid is used: UTM cells aligned to multiples of 1,000 m,
  each labelled with the nearest named suburb, neighbourhood or quarter
  (node position, or polygon centroid), with the distance recorded.
- A4. The ten areas or cells with the most flooded buildings (centroid rule)
  are reported, with flooded buildings, total buildings and flooded motor
  road length.

**Completeness warning**

- C1. On a 2 km UTM grid over the analysis area, cells are flagged "roads
  but no buildings" if they hold >= 2 km of motor road (R2) and no building
  centroid. Reported: number of such cells, their area, and the flooded area
  inside them.
- C2. Buildings per km of motor road, per 2 km cell, summarised as
  percentiles over cells with >= 2 km of motor road, and the same for the
  Srinagar box against the rest of the analysis area.
- C3. Nothing here corrects counts; it only warns where OSM may be missing
  buildings.

## 2. Water index (MNDWI)

Surface reflectance = DN x scale + offset, with green scale/offset [2.75e-05, -0.2] and SWIR1 scale/offset [2.75e-05, -0.2] (from DATA.md, identical for all scenes). Then MNDWI = (green - SWIR1) / (green + SWIR1), computed in float64 and saved as float32 GeoTIFFs `data/water/{pre_2014-08-25|flood_2014-09-10}_mndwi.tif` (NaN = no data or reflectance <= 0).

Where green or SWIR1 reflectance is <= 0, MNDWI is not meaningful (it can leave the range -1 to 1), so these pixels are masked rather than clipped or adjusted. Among them, clear valley-floor pixels with SWIR1 <= 0 but green > 0 would have MNDWI > 1, which points to water:

## Limitations noted

- Saturation: the MTL files report saturation present (Y/N) in green (band 3) / SWIR1 (band 6) as: `LC08_L2SP_149036_20140825_02_T1` Y/N; `LC08_L2SP_149037_20140825_02_T1` N/Y; `LC08_L2SP_149036_20140910_02_T1` Y/N; `LC08_L2SP_149037_20140910_02_T1` Y/N. QA_RADSAT was downloaded in step 3; it marks no green or SWIR1 saturation inside the clip box on either date (2014-08-25: 0 green / 0 SWIR1 pixels, 2014-09-10: 0 green / 0 SWIR1 pixels). The step 2 water masks were made before QA_RADSAT was available; with no saturated pixels in the clip box they are unaffected.
- QA_PIXEL misses some small clouds (visible near the Srinagar airport box on 2014-09-10, `previews/water_sanity_sites.png`). Unflagged cloud is counted as valid, not-water, and hides what is beneath it. Estimated in step 3, section U.
- The DEM is a surface model and its vertical datum is not stated in the files.
- The 2014-08-25 Otsu threshold is not well supported by its histogram (section 5); step 3 uses the 2014-09-10 threshold on both dates.
- Row 036 / 037 reflectance offsets (DATA.md) remain in the mosaic; their effect on the water class is in section 8.
- Water covered by vegetation (e.g. the Wular box on 2014-08-25) is not detected as water by MNDWI. Such areas that are open water on 2014-09-10 count as flooded.
- OpenStreetMap polygons are current (downloaded 2026-10-02T16:19:34+00:00), not a 2014 map.
- Building and road counts use today's OpenStreetMap, not 2014's, and OSM building coverage in the analysis area is patchy (step 4, completeness). Building counts are counts of mapped buildings only.
- Mosaic grid and clip box as in DATA.md (bbox [74.2, 33.5, 75.4, 34.6]).
